# Project context: what we built and why

Architecture and setup are documented in `README.md`; this file is the "why," not a restatement of what's readable from the code.

## Shared abstractions (why they exist)

All 4 gadgets share the same first config steps (Space → Sprint → Story Points Field → Status Mapping → Grace Window). Rather than duplicate that ~150 lines of state/loading/JSX per gadget, it's factored into:

- `useSprintSourceConfig.js` — the hook owning all of that state/loading/hydration
- `SprintSourceFields.jsx` — the presentational form for it
- `sprintConfigShared.jsx` — shared constants (`PHASE_OPTIONS`, `DEFAULT_PHASE_MAP`) and styles
- `useDisplayMode.js` — shared chart/table/both view-mode logic (TRI Scope Change, TRI Rework)

Each gadget's `Edit` component composes these and adds only its own extra fields (e.g. TRI Cycle Time's Hours-per-SP and Business Hours fields).

## Shared cache (why it's keyed the way it is)

`getSprintRawData()` in `src/index.js` fetches issues + full changelog for a sprint — the expensive part (pagination + changelog per issue) — and caches it via `@forge/kvs`, keyed by `(sprintId, storyPointsFieldId)`. This is deliberately **not** keyed by status mapping, because the mapping only affects the cheap compute step (classifying transitions into phases), not the fetch. Result: if two widgets on the same dashboard point at the same sprint and SP field — even with different status mappings — only one Jira fetch happens.

**`@forge/storage` vs `@forge/kvs` — don't reintroduce the former.** This app originally (incorrectly) depended on `@forge/storage` with `const { storage } = require('@forge/storage')`. That package's actual v2 API has no ready-made `storage` export at all (only low-level primitives like `GlobalStorage`/`getStorageInstanceWithQuery` meant for manual OAuth-client wiring) — so `storage` was `undefined` and every `storage.get`/`storage.set` call silently threw, swallowed everywhere by `catch (_) {}` except in two resolvers added 2026-07-27 that didn't swallow it, which is how this was caught (see bug #6 below). Caching had never actually worked in this app until it was fixed by switching to `@forge/kvs`'s `kvs` export — confirmed via Atlassian's current Storage API docs as the supported package. No manifest change was needed (`storage:app` scope covers both).

## Status/phase mapping model (the core abstraction)

There is no hardcoded status-name list anywhere. Every gadget works off a per-instance `statusMapping: { [statusName]: phase }` where phase is one of: `backlog`, `dev`, `blocked`, `review`, `test`, `done`, `excluded`. This is what lets one codebase work with any team's custom Jira workflow. `blocked` was added later (originally folded into `dev`) specifically so TRI Cycle Time could track blocked-time separately, matching the reference script's 4-bucket cycle-time table. Verified safe to add: burndown/scope-change/rework only special-case `review`/`test`/`done`/`excluded`, so an unrecognized-there `blocked` phase behaves like `backlog`/`dev` — no behavior change for those three.

## Dashboard sprint filter (why it's built this way)

TRI Sprint Filter is a 5th gadget added later so multiple TRI-* widgets on one dashboard can share a single Space/Sprint selection instead of each being configured separately. Jira dashboards have no native cross-gadget filter mechanism, so this is built entirely out of two Forge primitives working together:

- **`@forge/kvs`, keyed by `dashboard-filter:${context.extension.dashboard.id}`** — the durable source of truth. `dashboard.id` comes from the gadget's own context (confirmed against Atlassian's `jira:dashboardGadget` context docs — `context.extension.dashboard.id` / `context.extension.gadget.id`), not passed up from the client, so it can't be spoofed and needs no extra plumbing.
- **`@forge/bridge`'s `events.emit`/`events.on`** — for instant updates to gadgets already open on the same dashboard, without a page refresh. This channel is explicitly in-page-only and unpersisted (confirmed against Atlassian's Custom UI bridge events docs) — it does NOT replay past events to a late subscriber. That's why storage is still read on every gadget's mount: a gadget that mounts before, after, or without ever seeing the live event still picks up the current selection.

`useDashboardFilter.js` wraps that hybrid (poll storage on mount + subscribe to the live event). `useEffectiveSprintSource.js` sits on top of it and is what each of the 4 reporting gadgets' views actually call — it decides, per gadget, whether to use its own saved config or the filter's override, and never both partially.

**The status-mapping wrinkle, and the resolved tradeoff:** Status → Phase Mapping is keyed by a specific project's actual status names (see the section above), so it can't blindly follow a filter that might point at a different Space's differently-named workflow — doing so would silently classify every status as `backlog` with no error, which is worse than not following the filter at all. Resolved by: if the filter's Space matches what the gadget's mapping was configured against, use the saved mapping; if not, fetch that Space's statuses and apply the same `DEFAULT_PHASE_MAP` best-guess heuristic already used the first time a Space is picked in edit mode, and surface a "using a best-guess mapping" note in the view (`source.usingDefaultMapping`). This was a deliberate simpler-alternative chosen over the more correct-but-heavier option of storing a status mapping per-Space inside each gadget's config — reasonable because the expected use case is switching *sprints* within one project, not switching between differently-shaped projects on the same dashboard.

SP Field, Status Mapping, and Grace Window are never part of the filter override — only Space and Sprint are. A gadget must still be fully configured (its own Space picked, to seed the Status Mapping list) even when "Use dashboard sprint filter" is on.

## TRI Velocity (why it's structurally different from the other 5)

TRI Velocity is a 6th gadget (2026-07-28), adapted from an existing multi-team velocity gadget in another project. It deliberately does **not** use `useSprintSourceConfig`/`SprintSourceFields` — those assume one Space + one pinned/active Sprint, but Velocity always trends across a space's several most-recent **closed** sprints, so "which sprint" isn't a config choice at all.

- **Multi-space config.** A gadget instance can chart 1..N spaces (`VelocitySpaceRow.jsx`, one row per space).
- **Dashboard filter integration is Space-only, and single-space-only.** Because the filter's whole model is "pick one Sprint," and Velocity never shows just one sprint, following the filter's Sprint would be meaningless — so `useVelocityEffectiveSpaces.js` only ever overrides *which space* is charted, and only when the gadget is configured with exactly one space (with more than one, there's no single space to point the override at).
- **The Total chart (multi-space only) joins by recency rank, not calendar date.** Independently-scheduled boards rarely close sprints on the same day, so there's no shared date to sum by — `buildTotals()` in `TriVelocityGadgetView.jsx` aligns "most recent", "2nd-most-recent", etc. across spaces instead. A space with fewer closed sprints/completed iterations than others just doesn't contribute to the older ranks. Two related config flags: `showTotal` (adds the Total row) and `onlyShowTotal` (hides the per-space rows, showing only Total) — enforced consistent at save time in `TriVelocityGadgetEdit.jsx` (`onlyShowTotal` always implies `showTotal`), so the view never has to reconcile a contradictory combination.
- **Always fetches up to 10 closed sprints/completed iterations per space, viewer slices client-side.** Matches the existing "10 most recently closed" cap used elsewhere (`getSprintsForProject`) instead of inventing a new number. The viewer's 1–10 "sprints/iterations to show" selector just re-slices already-fetched data, so changing it doesn't trigger a resolver round-trip.

### TRI Velocity rework (2026-07-29): reads Capacity data instead of computing its own

The original design above (per-space SP Field/Status Mapping/Grace Window, `computeVelocity()` reusing TRI Burndown's grace-window math) was **replaced**, not extended, once the Capacity feature existed — duplicating the same committed/velocity math in two places (this gadget and the Capacity tab) meant they could silently disagree, and Capacity's category-based math already covers both Scrum and Kanban, which the old TRI-Velocity-only implementation never did (it was Scrum-only).

- **`getVelocityData` (`src/index.js`) no longer calls `getSprintRawData`/`computeVelocity` at all.** For a Scrum space it reads `capacity-rows:${projectKey}` (the same per-sprint overrides the Capacity tab's "Get SP Count"/"Get Velocity" buttons save) merged over `fetchClosedSprintsForBoard`'s sprint list; for a Kanban space it reads `kanban-iterations:${projectKey}` filtered to `status === 'completed'`. `computeVelocity()` itself is **not deleted** — it's still used by Capacity's own `getSprintVelocitySp` resolver, just no longer by this gadget.
- **A per-sprint/iteration row that was never calculated on the Capacity tab shows `0`, not an error and not a live computation.** This gadget is a pure reader now — it never triggers Capacity's "Get SP Count"/"Get Velocity" logic itself. If a user only ever looks at TRI Velocity and never opens a space's Capacity tab, they'll see zeros; that's expected, not a bug.
- **A new `capacity` value per row, sourced from `capacitySp` override → falls back to that space's `baseCapacitySp` Capacity setting** (`getCapacitySettingsFor()`, extracted from the `getCapacitySettings` resolver body so both can share the kvs-merge-with-defaults logic without duplicating it) — mirrors exactly how the Capacity tab's own `InlineNumberField` computes its displayed Capacity value, so the two surfaces never disagree about what "Capacity" means for a given row.
- **Edit screen's Space picker is filtered to Capacity-enabled projects only** (`getCapacityEnabledProjects`, new resolver next to `getCapacityPlanningEnabled`) — since a space with Capacity off has no `capacity-rows`/`kanban-iterations` data for this gadget to read. There's no bulk "projects with property X" Jira search endpoint, so this fetches the full (up to 100) project list and checks each one's `tri-capacity-planning` entity property individually via `Promise.all` — one-off cost, Edit-mode only.
- **Story Points Field, Status Mapping, and Commitment Grace Window all disappeared from this gadget's config entirely** — they live on the space's own Capacity Settings page now (`spFieldId`/`graceWindowHours` in `capacity-settings:${projectKey}`). `useVelocityEffectiveSpaces.js` lost its entire best-guess-status-mapping fallback subsystem as a result — overriding to a different space via the dashboard filter now just means reading that space's own Capacity data, with no config drift to reconcile (there's nothing left to drift).
- **New per-instance "show/hide Capacity bar" toggle** (`showCapacityBar`, default `true`) — `TriVelocityGadgetView.jsx`'s `BarGroup` renders a third (blue, `--brand`) bar alongside the existing Committed (amber, `--filling`) and Velocity (green, `--ok`) bars when on, reusing existing CSS tokens rather than inventing a new color.
- **Chart polish (same day, after first live check on `prediktivity.atlassian.net`):** `getVelocityData` now also returns each period's `startDate` (previously only `endDate`), so `TriVelocityGadgetView.jsx` can show the sprint/iteration's **name** plus a `dd/MMM - dd/MMM` date range under its bars (`fmtDDMMM`/`periodLabel`) instead of just the end date — the synthetic Total-chart rank rows (`buildTotals`, no name/dates of their own) still fall back to their rank label with no second line. Also gave the bar-group flex container `justifyContent: 'flex-end'` (briefly tried `space-evenly` first, replaced after the user pointed out it broke cross-space alignment) so every `SpaceRow`'s **most recent** period bar lands at the same right-hand edge regardless of how many periods that space has — a space with 1 period and a space with 3 both line their latest bar up vertically, which `space-evenly` couldn't do since it spread bars across the full width based on each row's own count. Tradeoff accepted, not fixed: when a row's periods overflow the container width, `flex-end` means the default (unscrolled) view shows the *oldest* visible periods, not the newest — scrolling right reveals more recent ones. This wasn't flagged as a problem and matches this app's general pattern of accepting a known edge case rather than adding scroll-position-management code for it.
- **Not a backward-compatible config migration.** A gadget saved before this rework still has its old `spFieldId`/`statusMapping`/`graceWindowHours` fields sitting in its stored config — `getVelocityData`'s new payload contract just ignores them (only reads `projectKey`). This doesn't crash, but a pre-existing gadget pointed at a space that's never had Capacity Planning turned on will silently show all-zero Committed/Velocity until either Capacity gets enabled for that space or the gadget is re-edited to point elsewhere. Documented in `README.md`'s Known Simplifications rather than auto-migrated, since there's no reliable way to backfill historical Committed/Velocity numbers Capacity was never asked to calculate.

## Capacity project tab (why it's not a dashboard gadget at all)

Added 2026-07-29 (infrastructure), real content added the same day. This is the first feature in the app that isn't a `jira:dashboardGadget` — it's a per-project ("space") tab living in Jira's own project navigation, not on a dashboard.

- **Two new modules, three new files.** `jira:projectSettingsPage` (key `tri-space-capacity-settings-page`, component `TriCapacitySettingsPage.jsx`) adds an on/off toggle under a project's Settings. `jira:projectPage` (key `tri-space-capacity-page`, component `TriCapacityPage.jsx`, currently a stub) is the actual "Capacity" tab shown alongside Summary/Board/Reports/etc. Both are registered in `static/gadgets/src/main.jsx`'s `GADGETS` map like every other module, just with only a `view` entry (no `edit` — these module types have no edit mode; `main.jsx`'s existing `entryPoint === 'edit' ? edit : view` fallback already handles that).
- **Why the toggle writes a Jira project property instead of `@forge/kvs`.** Forge's `displayConditions` (used to hide/show the Capacity tab per project) can only evaluate Jira/Confluence **entity properties** — they have no visibility into an app's own storage. So `TriCapacitySettingsPage.jsx` calls `setCapacityPlanningEnabled` (`src/index.js`), which `PUT`s `/rest/api/3/project/{projectKey}/properties/tri-capacity-planning` with body `{ enabled: true|false }` via the normal `asUser().requestJira()` pattern (the first `PUT`/write call to Jira this app has ever made — every prior resolver was read-only). `getCapacityPlanningEnabled` reads it back the same way, treating a 404 (property never set) as `enabled: false`, not an error.
- **Why the manifest's `displayConditions` looks the way it does.** `entityPropertyEqualTo` needs `entity: project`, the `propertyKey`, and — because the property value is a JSON object (`{ enabled: true }`), not a bare scalar — `objectName: enabled` to drill into it, compared against `value: "true"`. This mirrors the exact shape of Atlassian's own worked example for this display condition (a nested field). **Confirmed working against a real site 2026-07-29** — toggling the setting correctly shows/hides the Capacity tab after a project reload, no changes needed.
- **New scopes: `read:project.property:jira` / `write:project.property:jira`.** Granular scopes with no classic-scope equivalent for project properties — added alongside the existing scope list rather than replacing anything.
- **No control over tab position.** Forge's `jira:projectPage` manifest has no ordering/position property — confirmed against the current module reference docs. Placing the Capacity tab next to Reports (like Tempo/TimeTracker's tabs) is something a user does themselves via Jira's own tab reordering UI, not something this app configures.
- **Settings-toggle change isn't live on an already-open project tab.** `displayConditions` are evaluated when Jira renders the project's navigation, not reactively while a page is already open — so `TriCapacitySettingsPage.jsx` tells the user to reload the project after flipping the toggle, the same "not live, but durable" tradeoff as the dashboard sprint filter's storage fallback above, just without an events-bridge live-update path (there's no equivalent bridge between a Settings tab and the project's own nav chrome).
- **First real deploy briefly 404'd on the `jira:projectPage` URL itself (`/jira/software/projects/{key}/apps/{appId}/{envId}`), even though the tab correctly appeared/disappeared per the toggle.** This wasn't a manifest bug — the display-condition metadata (drives nav visibility) and the actual page-routing table (serves the URL) apparently propagate through Atlassian's backend at different speeds after `forge install --upgrade`. It resolved itself after a few minutes plus a hard browser reload, no code or manifest change involved. **If a future `forge install --upgrade` adding a new `jira:projectPage`/`jira:projectSettingsPage` module 404s immediately after deploy, wait and hard-reload before assuming something's broken.**

### Capacity content (Scrum + Kanban) — design decisions

- **Uses Jira's built-in status category, not the other gadgets' custom status→phase mapping.** `getProjectStatuses` already returns `categoryKey` (`new`/`indeterminate`/`done`) for free. `categoryBasedStatusMapping()` (`src/index.js`) turns that into a `{name: 'done'|'other'}` shape so Capacity can reuse `computeScopeFoundation`/`computeVelocity` completely unchanged — 'excluded' never appears, since Capacity has no equivalent concept. Kanban's own compute functions (`computeIterationCommitted`/`computeIterationVelocity`) use the category map directly instead of a statusMapping shim. This was a deliberate simplification chosen with the user over adding a whole second Status Mapping config UI.
- **`getBoardForProject` now reads `board.type`** (previously every board lookup in this file only ever used `board.id`) — this is how `getCapacityBoardInfo` decides whether a project gets the Scrum sprint table or the Kanban iteration table.
- **Team-managed ("next-gen") project boards always report `board.type: "simple"`, never `"scrum"`/`"kanban"`.** Confirmed live: a real team-managed Kanban board returned `type: "simple"`, which `getCapacityBoardInfo`'s original `board.type === 'kanban' ? 'kanban' : 'scrum'` check silently misread as Scrum. `resolveBoardType()` (`src/index.js`, right before `getBoardForProject`) only trusts `board.type` when it's literally `"scrum"` or `"kanban"` (i.e. classic/company-managed boards); otherwise it probes `GET /rest/agile/1.0/board/{id}/sprint?maxResults=1` — Jira returns 400 ("The board does not support sprints") for a sprint-disabled (Kanban-style) board and 200 otherwise, which works for both classic and team-managed boards. The probe only runs for the ambiguous `"simple"` case, so classic boards (the common case elsewhere in this file) never pay the extra request.
- **A manual "Board Type" override exists on the Capacity Settings page precisely because auto-detection can still be wrong** (e.g. an unusual board setup, or a future Jira platform quirk this app doesn't know about yet) — `capacity-settings:${projectKey}.boardTypeOverride` (`'auto'` | `'scrum'` | `'kanban'`, default `'auto'`). `getCapacityBoardInfo` returns both `boardType` (the effective, override-applied value every other resolver/frontend piece should use) and `detectedType` (the raw auto-detected value, ignoring any override) — the settings page shows the override dropdown alongside "(currently: detectedType)" so the user can see what auto-detect actually found before deciding whether to override it.
- **Scrum sprints stay real Jira objects; Kanban "iterations" are 100% app-invented**, stored in `@forge/kvs` under `kanban-iterations:${projectKey}` (full CRUD — Add/Edit/Delete/inline status change), since Kanban boards have no native grouping construct to hang a "sprint"-like object off. Per-row Capacity/Committed/Velocity overrides for Scrum live in one blob per project (`capacity-rows:${projectKey}`, keyed by sprint id) rather than one KVS key per row, so listing sprints only ever needs a single `kvs.get`.
- **Scrum's edit dialog uses `POST /rest/agile/1.0/sprint/{id}` (partial update), not `PUT` (full update)** — deliberately, since the dialog only edits Goal + dates and never Name; a full-update `PUT` would require re-sending every field and risks clobbering something omitted. New scope: `write:sprint:jira-software` (confirmed against Atlassian's own REST API docs) — the app's first-ever write to a *content* resource (as opposed to the project-property toggle, which is metadata).
- **Kanban's committed/velocity JQL is intentionally asymmetric.** Committed's JQL is just a pre-filter — the actual "was it committed at the cutoff" check happens via `statusAt()` reconstruction from the changelog (see the 2026-07-29 Committed-status-whitelist entry below for what the pre-filter looks like now). Velocity bounds tightly on `resolved >= start AND resolved <= end` (Jira's `resolutiondate`, a much closer proxy for "when this finished" than `updated`) since only issues that actually moved to Done inside the window matter, cross-checked against the real transition timestamp in `computeIterationVelocity`. This is the same class of engineering approximation as `getSprintRawData`'s uncapped pagination — a documented tradeoff, not silently ignored.
- **Kanban's Committed calculation switched from a fixed status-category check to a configurable status whitelist (2026-07-29 fix).** The category-only version (`statusCategory != "To Do"`) had a real bug reported by the user: a team's custom status ("Team Estimated") was categorized "To Do" by Jira but was meant to count as already-committed — since the JQL pre-filter itself excluded "To Do"-category issues, tickets sitting in that status were never even fetched, so no amount of post-processing could have counted them. Fixed with a new Kanban-only Capacity setting, `kanbanCommittedStatuses: string[]` (default `[]`, meaning "not customized yet") — `defaultCommittedStatusNames(categoryMap)` (`src/index.js`, next to `getCapacityStatusMapping`) computes the category-based default (every indeterminate/done status) so an un-customized project behaves identically to before. The JQL pre-filter now uses `status WAS IN (...)` (a JQL historical-value operator) over the *effective* committed-status list instead of `statusCategory != "To Do"` — deliberately `WAS IN`, not `IN`, since an issue needs to be caught even if it's since moved on to some other status (e.g. Done) after being committed at the cutoff; a current-status-only `IN` would miss it. `computeIterationCommitted()` was correspondingly changed from a category lookup to a plain `Set.has()` membership check against the same list. `TriCapacitySettingsPage.jsx` shows one checkbox per project status (via the existing `getProjectStatuses` resolver, reusing `statusStyle()` for the category chip), pre-checked to the category-based default until the user overrides it, plus a "Reset to default" link that clears the override back to `[]`. This setting is Kanban-only and affects Committed only — Scrum's committed math (`computeScopeFoundation`) and Kanban's own Velocity calculation are both untouched by it.
- **The unbounded `status WAS IN (...)` from the fix above caused a real 25-second Forge function timeout on a live, long-running Kanban project (same day).** `WAS`/`CHANGED`-family JQL clauses without a date bound force Jira to scan every matching issue's *entire* changelog history — with no date qualifier, `status WAS IN (...)` effectively asked "did this status ever hold one of these values, at any point since the issue was created", pulling in every issue that passed through a committed status at any point in the project's whole history (including ones resolved long ago and untouched since), then fetching each one's full changelog on top. Fixed by adding a `DURING ("start", "end")` bound (`getIterationCommittedRawData`, `jqlDateOnly()` helper) — a ±2-day window around the exact grace-window cutoff instant, not around "now" or around the whole iteration. The ±2 days isn't slack for the grace window itself (that's already baked into `cutoffMs` before the window is computed) — it's slack for JQL date literals being evaluated in the *site's own configured timezone*, which can disagree by up to a day with our UTC-computed cutoff date; padding both directions means the pre-filter can only ever be too broad, never too narrow, so `computeIterationCommitted`'s exact-hour `statusAt()` check afterward is still the actual source of truth. The raw-data cache key also gained a `:${cutoffMs}` suffix, since the fetched set is no longer valid for every possible cutoff the way the old unbounded query was (moot today since `getIterationCommittedSp` always force-refreshes, but correct if that ever changes). **If any other Kanban Capacity resolver is ever built on a `WAS`/`CHANGED` JQL clause, bound it with `DURING`/`AFTER`/`BEFORE`/`ON` from the start — this is Atlassian's own documented performance guidance for these operators, not something to rediscover the hard way again.**
- **Two more Committed correctness fixes, prompted by the user asking "how does your query work" and pressure-testing the answer (same day):** (1) **`defaultCommittedStatusNames()` no longer includes Done-category statuses** — only `indeterminate`. The original spec for Kanban's Committed was explicitly "in progress statuses at the start of the iteration"; Done had been folded into the default by loose analogy to Scrum's initial-scope math (which does count already-done sprint items), but for Kanban this let a ticket finished long before a brand-new iteration even existed keep counting as "committed" to it forever afterward, since a terminal Done status never changes again — every future iteration's `WAS IN (...) DURING (...)` window would still find it sitting there. Confirmed with the user (they picked "Exclude Done by default" over two alternatives) before changing it; a Done-category status can still be checked explicitly in the settings checklist if a workflow genuinely needs it. (2) **`computeIterationCommitted` now skips any issue `created` after the cutoff outright**, regardless of what `statusAt` reports for it — an issue created after the cutoff didn't exist yet, so even if it was created directly into a whitelisted status, that's mid-iteration scope creep, not something genuinely committed at the start (the Kanban equivalent of what the Commitment Grace Window already protects Scrum's `computeScopeFoundation` against). The user suggested this directly. The JQL pre-filter also gained `AND created <= "${windowEnd}"` (same padded window-end used for the `DURING` bound) purely to shrink the candidate set further — the exact per-issue `created` check in `computeIterationCommitted` is what actually enforces this, so the JQL bound being a day or two loose from timezone rounding can't cause an incorrect result, only a slightly larger (still correct) fetch.
- **Kanban's optional label filter is per-iteration, not project-wide** (`labelFilter` field on each iteration record) — confirmed with the user; different iterations can track different release-train labels. Originally Velocity-only; the user first asked to also apply it to "Get SP Count" (since an iteration scoped to a release label was still counting *every* matching-status issue in the project toward Committed, not just that release's), then immediately reconsidered and asked to make it a settings toggle instead, off by default — whether a release label should scope "what counts as committed" is a per-project judgment call in a way Velocity's "what counts as done for this release" isn't. Landed as a new Kanban-only Capacity setting, `kanbanCommittedUsesLabelFilter` (boolean, default `false`). `computeIterationCommitted` still takes a `labelFilter` parameter (same `labelFilter && !(issue.labels || []).includes(labelFilter)` skip as `computeIterationVelocity`), but `getIterationCommittedSp` only passes `iteration.labelFilter` through when the setting is on — otherwise it passes `''`, so existing un-customized projects see no behavior change. `fetchIterationIssues` already fetched `labels` for Velocity's sake, so no new field was needed on the issue-fetch side. UI: a dedicated "Apply Label Filter to Committed" section in `TriCapacitySettingsPage.jsx`, next to Committed Statuses.
- **Enforcing "only one active Kanban iteration" blocks rather than auto-flips** (`checkSingleActiveIteration`, shared by `saveKanbanIteration` and `setKanbanIterationStatus`) — confirmed with the user: the app never silently changes a row the user didn't touch. Attempting to activate a second iteration while one is already Active (and `kanbanAllowMultipleActive` is off) returns an error naming the conflicting iteration.
- **`statusAt(transitions, atMs)` and `graceCutoffMs(startDateISO, graceWindowHours)` were lifted out of `computeBurndown`/`computeScopeFoundation`** into top-level functions so Capacity's Kanban compute path could reuse them — pure refactors, no behavior change for the 4 original gadgets.
- **`router.open()` accepts a relative path** (confirmed against Forge's bridge docs) — the Scrum tab's "Open Backlog" link uses `/jira/software/projects/{key}/boards/{boardId}/backlog` directly, no need to resolve the site's absolute base URL.
- **Scrum's "show closed sprints" count is user-selectable (3/5/10/15/All), not a fixed 10.** `getScrumSprintsForCapacity` takes an optional `closedLimit` payload field (`resolveClosedLimit()` validates it against `CAPACITY_CLOSED_LIMIT_OPTIONS` or falls back to the original default of 10). "All" isn't literally unbounded — `CAPACITY_CLOSED_SPRINT_ALL_CAP` (100) caps it, same known-simplification class as the uncapped-pagination limitation below. `CapacityScrumTab.jsx` only shows the dropdown once "Hide closed sprints" is unchecked, and passes the choice into `useCapacityRows` via its new `listParams` option (spread into the list resolver's invoke payload, keyed off `JSON.stringify` for the reload dependency).
- **Kanban's matching "show completed iterations" count (same 3/5/10/15/All options) is purely client-side, not a resolver parameter** — unlike Scrum, `getKanbanIterations` already returns the whole per-project KVS array in one call (no server-side pagination to parameterize), so `CapacityKanbanTab.jsx` just sorts completed iterations by `endDate`/`startDate` descending and slices to the chosen count in the component, alongside the always-shown non-completed rows.
- **Scrum's `computeVelocity` was drastically simplified (2026-08-12 fix), dropping the grace-window/history-walk logic entirely.** The original version reconstructed committed scope, per-day scope deltas, and removed/excluded timestamps (via `computeScopeFoundation`) purely to gate a "did this issue transition into Done by end-of-sprint" check against each issue's transition history — mirroring `computeBurndown`'s point-in-time reconstruction even though Velocity never needed a specific past instant, only "what's Done right now." Reported by the user as a real discrepancy against Jira's own Sprint Report (85 SP Done there vs 72 SP from this gadget for a real closed sprint, `APO`/`260812-Sprint 10`). Root-caused to two things: (1) needless complexity that made the number hard to reason about, and (2) a real caching bug — `getSprintVelocitySp` only passed `forceRefresh: true` to `getSprintRawData` when `sprint.state === 'active'`, so a **closed** sprint's cached issue snapshot (5-minute TTL, `ACTIVE_CACHE_TTL_MS`) was reused forever once written, with no way to force a refetch — if a batch of tickets moved to Done in the day or two before the sprint closed, after that cache was populated, Velocity would silently undercount by exactly that batch. Fixed by rewriting `computeVelocity(issueData, statusMapping, excludedStatuses)` to just sum SP of every issue whose **current** status (`issue.currentStatus`) maps to `'done'` in the same category-based `statusMapping` Capacity already builds (`getCapacityStatusMapping`) — equivalent to a plain `sprint = X AND status in (Done)` JQL query, no time range, no grace window, no removed-from-sprint tracking. `getSprintVelocitySp` now always force-refreshes `getSprintRawData`, since it's an explicit "Get Velocity" button click, not a page load — there's no scenario where serving a stale cache for it is correct. **`computeVelocity`'s old `{committed, completed, endDate}` return shape is gone — it now just returns a number.** Scrum's Committed calculation (`computeScopeFoundation`, used by `getSprintCommittedSp`) and TRI Burndown/Scope Change/Rework/Cycle Time are untouched — this was Velocity-only.
- **Follow-up same day: a new `excludedDoneStatuses` Capacity setting excludes specific Done-category statuses from both Scrum's and Kanban's Velocity.** After the simplification above, the user tested against the real sprint and found Velocity still counted a "Not Required" status — confirmed live: that status genuinely has `statusCategory.key === 'done'` in this site's Jira, and its `resolution` field is `null`, so there is no reliable Jira-provided signal to tell "genuinely completed" apart from "cancelled/not needed" once a project uses a custom status like this. Same root problem, and same fix shape, as the pre-existing "Kanban's Committed calculation switched from a fixed status-category check to a configurable status whitelist" entry above (a custom status Jira categorizes one way, a team treats another) — deliberately not hardcoded to the literal name "Not Required" (would silently miss any other team's differently-named cancelled/won't-do status), so a new per-project `excludedDoneStatuses: string[]` setting (default `[]`) was added instead, alongside the existing Capacity settings in `CAPACITY_SETTINGS_DEFAULTS`. `computeVelocity` (Scrum) now skips any issue whose current status is in this set before checking category; `computeIterationVelocity` (Kanban) skips any transition whose target status is in this set when looking for the issue's first real Done transition — checked at the transition level there, not current-status, since Kanban velocity is keyed off *when* an issue became Done, not just its current state. Both `getSprintVelocitySp` and `getIterationVelocitySp` now read `getCapacitySettingsFor(projectKey)` and pass `new Set(settings.excludedDoneStatuses)` through. UI: a new "Excluded Done Statuses" section in `TriCapacitySettingsPage.jsx`, shown for both Scrum and Kanban (unlike the Kanban-only Committed Statuses section) — one checkbox per Done-category project status, empty by default so an un-customized project's Velocity is unchanged. Has no effect on Committed (either Scrum's or Kanban's) — deliberately Velocity-only, since Committed already has its own separate, longer-standing status-whitelist mechanism (`kanbanCommittedStatuses`) for Kanban and doesn't use category matching for Scrum's Done-ness at all.

- **Release Mapping (2026-08-18): sprints/iterations can be mapped to a Jira version (fixVersion), with a Releases summary rollup above the Capacity table.** New opt-in Capacity setting `releaseMappingEnabled` (default `false`) plus `releaseThresholdPct` (default `70`) — confirmed with the user to apply to **both** Scrum and Kanban, even though Kanban "iterations" are this app's own construct with no native Jira entity; the mapping is just `iterationId -> versionId`, stored the same way as `sprintId -> versionId`. Storage deliberately reuses each board type's existing per-row override plumbing rather than a new KVS structure: `releaseId` was added straight into Scrum's `capacity-rows:${projectKey}` blob (via `setSprintReleaseId`, mirroring `setSprintCapacityOverride`) and into each Kanban iteration record (via `setIterationReleaseId`, mirroring `setIterationCapacity`) — same "minimal diff over existing round-trip" reasoning as `excludedDoneStatuses`. New resolver `getReleaseOptions` fetches the project's full, unfiltered version list from `GET /rest/api/3/project/${projectKey}/versions` (unpaginated — simpler than the paginated singular `/version` endpoint, fine for typical project version counts); no new manifest scope, since `read:jira-work` (already granted) covers it. **Deliberately returns released+archived versions too, not just unreleased ones** — the frontend (`ReleaseSelectCell` in `CapacityTableShared.jsx`) filters to unreleased+unarchived (plus whatever's currently assigned, so an existing assignment never vanishes from its own dropdown) for the *editable* `<select>`, but read-only cells and the Releases summary table need to resolve a name for *any* previously-assigned id, including ones that have since shipped. Read-only trigger is the sprint/iteration's own closed state (`sprint.state === 'closed'` / `it.status === 'completed'`) — confirmed with the user, deliberately **not** the release's own released/archived flag, so a still-open sprint stays editable even if its assigned release ships mid-sprint. The new `ReleasesSummaryTable` groups whatever rows are currently visible in the Capacity table (so it respects the existing hideClosed/hideCompleted + closedLimit/completedLimit filters unchanged) by `releaseId`, and — per explicit user confirmation — ships a Status indicator now rather than deferring it, with three tiers (worst first): **Over Capacity** (Total Committed > Total Capacity — no buffer left at all, the threshold is moot), **Over Threshold (N%)** (still within capacity but has eaten into the threshold's reserved buffer), **Within Threshold (N%)** — using each row's *effective* capacity (`capacitySp ?? baseCapacitySp`, matching what `InlineNumberField` actually displays) since raw `capacitySp` is frequently `null` for non-overridden Scrum rows. The threshold percentage is baked directly into the Within/Over Threshold labels so it's visible without a separate column. Avg Velocity is only averaged over rows where `velocitySp != null && velocitySp > 0` — a future/in-progress sprint's velocity reads as 0 long before it means anything, so including it would drag a release's average down purely because it isn't finished yet, not because the sprints that did finish underperformed (confirmed with the user against a concrete example: a release with 1 completed sprint at 45 SP and 4 not-yet-complete sprints at 0 should average 45, not 9). **Known limitation, not a bug:** if a project's Board Type override is later flipped (Scrum ↔ Kanban), release mappings recorded under the previously-active tab's storage become invisible on the Capacity page, since each tab only reads its own row source — inherent to Scrum/Kanban already being separate storage models, not new. No changes to any compute function (`computeVelocity`, `computeScopeFoundation`, etc.) — this feature is purely additive metadata plus a client-side rollup.

## TRI Release Capacity (2026-08-18)

New `jira:dashboardGadget` — a cross-project view of Release Mapping data, since the Capacity page's own Releases summary table (above) is inherently per-project. Two chart modes, per a user-supplied reference implementation from a different app ("Release Planning"): **By space** (one release, one hand-drawn bar per configured space, plus a Total column) and **By release** (one space's roadmap: current release + N upcoming ones, one bar each). Architecturally a sibling of TRI Velocity — "config picks spaces, each space's own Capacity data drives everything" — not a new compute pipeline.

- **Cross-space release matching is by NAME, not id — a deliberate, user-confirmed constraint, not an oversight.** Jira `fixVersion`s are per-project entities; there's no shared cross-project release object to match on. When a viewer picks a specific release from the live dropdown, `getReleaseCapacityRollup` (`src/index.js`) looks up each space's *own* version whose `name` matches exactly. Teams that don't name releases consistently across projects will see some bars come up empty for a given name — expected, not a bug.
- **Auto-select is a per-space rule, not a name-matched one — so different bars can legitimately show different release names in Auto mode.** `pickAutoVersion(versions, todayISO)` picks the soonest-upcoming unreleased version by `releaseDate` (falling back to the most recent past unreleased version, then any undated unreleased version, else `null`), independently per space. `todayISO` is passed in from the browser (`localTodayISO()`), not computed server-side — same UTC-lag reasoning as every other "today" calculation in this app.
- **The Release selector is a live control in the View, session-only — not persisted.** Confirmed with the user, matching an already-established precedent: TRI Velocity's `sprintCount` selector is the same shape ("Viewers can change this on the gadget itself" — Edit sets a default, View starts there, no `view.submit` on change). `config.releaseName` (`null` = Auto) is only the starting value.
- **The space picker only offers Release-Mapping-enabled spaces.** `getCapacityEnabledProjects` gained a second optional filter, `releaseMappingFilter`, applied after the existing `boardTypeFilter` — one extra `kvs.get('capacity-settings:...')` per already-Capacity-enabled project, same bounded/Edit-mode-only cost class as `boardTypeFilter`'s extra board lookup.
- **`fetchProjectVersions(projectKey)` was extracted from `getReleaseOptions`** into a plain internal function so `getReleaseCapacityRollup` doesn't duplicate the Jira versions fetch — `getReleaseOptions` is now a thin wrapper.
- **`getReleaseCapacityRollup` fetches Scrum rows more broadly than the Capacity page's own default** — active + future + **all** closed sprints (`fetchSprintsByState(board.id, 'closed', 'all')`, same `CAPACITY_CLOSED_SPRINT_ALL_CAP`-capped 100-row ceiling the Capacity page's own "All" closed-sprint option already uses), since a release can span sprints well older than the Capacity page's default 10-closed-sprint view. Kanban just reads `getIterations(projectKey)` (already unpaginated).
- **The resolver also returns each space's display `name`** via the existing `getSpaceName()` helper (kvs-cached) — a late addition during implementation once it became clear the View has no other way to know a project's display name (unlike Edit, which already has it from `getCapacityEnabledProjects`'s own result). Mirrors `getVelocityData`'s identical reason for calling `getSpaceName`.
- **Shared three-tier classification, not shared colors.** `classifyReleaseStatus(totalCommitted, totalCapacity, thresholdPct)` was extracted from the Capacity page's `ReleasesSummaryTable` (`CapacityTableShared.jsx`) into `gadgetUtils.js`, returning just a `tier` (`'none'|'within'|'overThreshold'|'overCapacity'`). `ReleasesSummaryTable` keeps its existing chip presentation unchanged (both over-tiers still render red) — only this gadget's bars use the full state distinction (`OK`/`FILLING`/`OVER`/`SET CAP`, matching the reference implementation's wording), via `--ok`/`--filling`/`--over` tokens already defined in `styles.css` for both themes.
- **Chart is hand-drawn `<div>`, not a charting library — replaced an initial recharts `ComposedChart` version the same day, per the user's supplied reference gadget.** TRACK_H bar columns (`TriReleaseCapacityGadgetView.jsx`) with an absolutely-positioned fill div, a state chip, and (`By release` mode only) a CURRENT/FUTURE chip above it — same visual language as TRI Velocity's own hand-rolled `BarGroup`/`SpaceRow`, not recharts.
- **Bars are scaled by %-of-own-capacity, not absolute story points — the fix that finally made one flat Threshold/Capacity line correct for BOTH chart modes, after three rounds of user-screenshotted correction.** Round 1: an SVG polyline connecting each bar's own differing absolute threshold/capacity value — the user screenshotted the reference's actual flat-line behavior and said that's what's wanted instead. Round 2: one flat line using an aggregate absolute-SP reference (sum across spaces for "By space"; the anchor/current release's own absolute capacity for "By release") — the user then screenshotted "By release" mode specifically breaking: a release at 80/50 pts (160%, correctly labeled OVER) rendered with its bar sitting well below the shared cap line, because that line was drawn at a *different* release's absolute capacity (200 pts), not that bar's own. A `perBarLines` special case was added for "By release" mode (per-bar tick marks instead of a shared line) to work around it. Round 3: the user screenshotted "By space" mode too — bars visibly weren't scaled to the already-correct line position (e.g. a 220/200 = 110% OVER bar rendering *shorter* than an 83%-full bar), because bar height was still computed as `committed / (shared absolute-SP maxScale)`, an entirely different scale than the line's aggregate-SP position. **Root cause common to all three rounds:** mixing an absolute-story-point scale (which is only ever comparable across bars with the same capacity) with a chart that legitimately has different capacities per bar. **The actual fix:** switch the whole Y-axis to %-of-each-bar's-own-capacity (`pctOfCapacity = totalCommitted / totalCapacity * 100` — literally the same number already shown in the label, e.g. "220/200 pts · 110%"). On this scale, "100% of capacity" is *always* the same relative height for every bar regardless of its absolute capacity, so ONE flat cap line is correct in both modes with no special-casing (`perBarLines` removed entirely). The threshold line's %-of-capacity value is a blended aggregate (`total threshold SP / total capacity`) across whatever's on screen — in "By space" mode this is a real approximation across spaces with potentially different individual %; in "By release" mode every item shares one project's single threshold %, so the identical aggregate formula reduces to that exact value with no approximation. **Lesson:** a flat reference line and per-bar-scaled heights have to live on the *same axis* — putting one on a relative (%) scale and the other on an absolute one is what produced two visibly-wrong iterations before this was caught.
- **No stacked per-team segments** in `By release` mode (the reference's `ByVersionBars` stacks by team; this app's model has no sub-entity inside one space's release rollup, so a roadmap bar is a single plain value), and **no "Open in Release Planning →" deep link** (no analog page exists here).
- **"By release" mode's live header control is "Releases to show" (a count), not a release picker — the release-name dropdown made no sense once the mode already only ever shows ONE space's roadmap starting from its own configured "Current release."** The header now shows the selected space's name as plain text (via `getReleaseRoadmapRollup`'s new `name` field, same `getSpaceName()` reasoning as `getReleaseCapacityRollup`) plus a live `futureCount` `<select>` (same `Edit`-sets-default/`View`-starts-there-and-can-change convention as TRI Velocity's `sprintCount` and this gadget's own "By space" release dropdown) — changing which release is "current" stays an Edit-only choice for this mode; "By space" mode's release-name dropdown is unaffected. All "version" wording was renamed to "release" throughout both files (`Current version` → `Current release`, etc.) for consistency with the rest of the app's vocabulary.
- **`getReleaseRoadmapRollup` (new resolver) powers "By release" mode** — one space, an ordered roadmap of releases. `buildReleaseRoadmap(versions, anchorVersion, futureCount)` always includes the anchor first (regardless of its own released/archived state, since a manually-picked "current version" could be anything) followed by the next `futureCount` unreleased/unarchived versions ordered by `releaseDate` (undated last). Both this resolver and `getReleaseCapacityRollup` now share `fetchReleaseMappedRows(projectKey)` (board/boardType lookup + Scrum-or-Kanban row fetch) and `rollupForVersion(rows, targetVersion, settings)` (pure sum, no I/O) — factored out so the roadmap resolver fetches a project's rows **once** and reuses them across every release in the roadmap, instead of refetching per release. Both resolvers key their anchor/target release the same way — by `releaseName`, not id — so the Edit screen's single "Default Release"/"Current version" config field and the View's live dropdown work unchanged across both modes.
- **No new manifest scopes.** Everything reads data already covered by `read:jira-work`/`storage:app` (project versions, `@forge/kvs` capacity data, Jira Agile sprint/board endpoints). The `MAJOR_VERSION_RULE` approval `forge lint` flags on this change is Forge's standard "module set changed" gate for adding any new gadget module — confirmed via `git diff manifest.yml` that only a new `jira:dashboardGadget` entry was added, no `permissions.scopes` change.
- **Icon temporarily borrows `tri-velocity.svg`**, same "ship now, dedicated icon later" convention as the three Kanban gadgets (see bug #5) — swap in a dedicated SVG under `static/gadgets/public/icons/` and push to whatever ref `icons-v4` points at when one exists.

### Epic story-point rollup — applies to every gadget, not just Capacity

- **An Epic's own SP field is a fallback, never the source of truth, when it has children.** `resolveIssueSpValues()` (`src/index.js`, right after `getBoardForProject`) is called from both `extractRawSprintData` (Scrum) and `extractIterationIssueData` (Kanban) — the two functions every gadget's `issueData` ultimately comes from (Burndown, Scope Change, Rework, Cycle Time, Velocity, and both halves of Capacity). For any issue whose `issuetype.name === 'Epic'`, `fetchEpicChildrenSp()` queries `parent = <epicKey>` and sums the children's SP field; the Epic's own field is only used if that query comes back empty (no children, or the site doesn't support `parent`-based hierarchy — the query just returns nothing either way, no error path needed).
- **Why `parent`, not the classic "Epic Link" custom field:** Atlassian's Cloud hierarchy migration made `parent` the unified field for Epic↔child relationships across both team-managed and company-managed projects. Deliberately not implemented: a fallback lookup of the "Epic Link" custom field ID — if a very old/misconfigured site doesn't have `parent` wired up, the rollup silently no-ops and the Epic's own value is used, which is the same behavior as today. Not verified against a live site in this session (WebFetch/WebSearch were unavailable when this was implemented) — if an Epic's rollup ever looks wrong on a specific site, this is the first thing to check.
- **This both fixes and doesn't fully fix Kanban's Committed/Velocity scan.** Kanban's project-wide JQL (see above) has no issue-type filter, so it was already pulling in Epic issues whenever they matched the status/date criteria, contributing whatever (often blank/stale) value sat in the Epic's own SP field. The rollup fixes that number. It does **not** guard against double-counting: if an Epic's children independently also match the same scan (a very plausible case for Kanban, since both an Epic and its child stories can easily share an "In Progress" status at once), those children's SP is counted both via their own row and via the Epic's rollup. Documented as a known, accepted simplification (see `README.md`) rather than solved with cross-issue dedup, which would need every issue's `parent` fetched and cross-referenced, not just Epics'.
- **No new manifest scope needed.** `parent` is a standard Jira field returned by the same `/rest/api/3/search/jql` endpoint already used everywhere else in this file, under scopes already granted (`read:jql:jira`, `read:issue-details:jira`).

## Real bugs found and fixed — don't reintroduce these

1. **`snapToBizDay` must only roll Saturday/Sunday forward to Monday.** An earlier version snapped ANY pre-sprint date forward to the sprint's start day (`bizDays.find(b => b >= d)`), which double-counted committed scope: a ticket added before the sprint started got counted both in the initial committed-scope sum AND as a same-day "add" delta, making all burndown lines start at roughly double the ideal line's height.

2. **Never compare Jira timestamps as raw strings.** Jira's changelog `created` timestamps keep the site's local UTC offset (e.g. `+10:00`); `new Date(...).toISOString()` always normalizes to `Z`. String-comparing a `+10:00` value against a `Z` value is unsound near boundaries even though it "looks" ISO-8601. Every comparison in `src/index.js` goes through `Date.parse()` to compare actual epoch milliseconds.

3. **"Today" for burndown truncation must come from the browser, not the resolver.** Forge resolvers run server-side in UTC. For a site east of UTC (e.g. Sydney, UTC+10), `new Date()` on the server can still say "yesterday" well into the local morning — silently chopping the current day off the chart. Fixed by having the frontend compute `localTodayISO()` (`gadgetUtils.js`) from the browser's actual local date and pass it to the resolver as `todayISO`, instead of trusting server-side `new Date()`.

4. **The Commitment Grace Window (default 12h) only works if a sprint's `startDate` reflects when it was actually started.** If a team backdates the start date (e.g. enters a date a week before they actually click "Start Sprint"), there's no way to detect or correct for this via the Jira API — a Sprint has no field recording "the actual moment it was activated" separate from the editable `startDate`. This is why the grace window is user-configurable (per gadget instance) rather than hardcoded — it's the escape hatch for that workflow, not a bug to fix algorithmically.

5. **`jira:dashboardGadget.thumbnail` requires an absolute URL.** There is no manifest syntax for pointing it at a path inside a declared static `resource` — confirmed against Atlassian's own docs. Icons are hosted via `raw.githubusercontent.com/wodutoit/jira-tri-burndown-change-dashboard-gadget/<tag>/...`, pinned to a git tag (not a branch) so the URL can't silently change. **If icons are ever regenerated: create a new tag, and update all `thumbnail` URLs in `manifest.yml` to point at it.** As of 2026-07-31, every gadget's `thumbnail` is pinned to **`icons-v4`** — all 9 gadgets now reference the same tag (the three Kanban gadgets added the same day still borrow the closest existing gadget's icon file, e.g. `tri-burndown.svg` for Burnup — see the section above — `icons-v4` doesn't add any new icon files over `icons-v3`, it was just cut to re-pin the whole manifest to one current tag). `icons-v1`/`icons-v2`/`icons-v3` still exist in git history but nothing in `manifest.yml` should point at them anymore.

6. **`@forge/storage`'s `const { storage } = require('@forge/storage')` pattern silently did nothing — every call failed and was swallowed.** That package's actual v2 API (installed: 2.0.3) has no ready-made `storage` export, only low-level primitives requiring manual OAuth-client wiring not meant for direct app use. `storage` was `undefined`, so every `storage.get`/`storage.set` threw "Cannot read properties of undefined (reading 'get'/'set')" — invisible everywhere because every call site wrapped it in `catch (_) {}`. Caching had silently never worked (confirmed: the "· cached" indicator had never once appeared in testing) until the two new dashboard-filter resolvers (2026-07-27), which don't swallow the error, surfaced it in the UI. Fixed by switching to `@forge/kvs`'s `kvs` export, the package Atlassian's current docs confirm is actually supported. **If you ever see "Cannot read properties of undefined (reading 'get'/'set')" again, check for a stray `require('@forge/storage')` before assuming it's something else — this exact failure mode is easy to reintroduce by copying an old snippet.**

7. **A closed sprint's `endDate` is the originally scheduled end date, not when it was actually closed.** Jira never updates `endDate` if a sprint runs past it — a scrum master who clicks "Complete Sprint" a few days late leaves `endDate` exactly as originally planned. Every date-ranged computation (`computeBurndown`, `computeScopeChangeData`, `computeReworkData`, `computeCycleTimeData`) used `sprint.endDate` directly as the chart/table's last day, so a sprint closed late had its real tail — status transitions, scope changes, rework, cycle time — silently cut off at the stale planned date instead of the real one. The real close time is in `sprint.completeDate` (only present once a sprint is closed), fetched by `resolveSprint()`'s existing call to `/rest/agile/1.0/sprint/{sprintId}` but never read anywhere. Fixed with an `actualSprintEnd(sprint)` helper (`src/index.js`, near `getBusinessDays`) — returns `completeDate` when it's later than `endDate`, else `endDate` unchanged — used everywhere `sprint.endDate` previously fed a chart's date range or a cycle-time truncation point. This is the same class of bug as #4 above (Jira's editable sprint-boundary fields lagging reality), just on the end side instead of the start side — but this one has an actual authoritative field to correct against, so it didn't need a user-configurable escape hatch like the grace window.

8. **`new Date(iso + 'T00:00')` followed by `.toISOString().slice(0, 10)` silently rolls the date back a day for any timezone ahead of UTC.** `CapacityKanbanTab.jsx`'s "add a new iteration" defaults used exactly this pattern to compute "latest end date + 1 day": `new Date(iso + 'T00:00')` parses the string in the *browser's local* timezone, `.setDate(d.getDate() + 1)` correctly adds a day in local time, but `.toISOString()` then converts back to UTC — for a site east of UTC, local midnight is still the previous day in UTC, so the +1 gets cancelled out and the "new" start date comes out identical to the old end date. Same bug, same root cause, same fix pattern as #3 above (local-time math must never round-trip through `.toISOString()`), just triggered by explicit date arithmetic instead of `new Date()`'s implicit "now". Fixed with `addDaysToISODate(iso, days)`, which builds the result via `Date.UTC(y, m-1, d+days)` directly from the string's own components — no local timezone ever enters the calculation, so there's nothing to round-trip incorrectly. Also fixed the iteration's End date default (`start + defaultLengthWeeks*7 days`), which had the identical latent bug one line down, not yet reported but structurally identical.

9. **`statusAt()` returned the literal string `'unknown'` for an issue with zero recorded status transitions — silently excluding it from every status-based calculation.** Jira's changelog only records *changes*; a ticket created directly into a status and never moved since has no transition entry to reconstruct its original status from, so `statusAt` fell through to `'unknown'`, which can't match any real status name or category. Reported as "Kanban's Get SP Count never returns a value" for a single-Kanban-team project (DEV4/Cylon) — nearly all of that team's tickets sit in a custom "committed" status (e.g. "Team Estimated") from creation and are never explicitly transitioned into it, so every one of them hit this fallback and Committed came out `0` every time, regardless of the Committed Statuses whitelist (see the "Kanban's Committed calculation switched..." entry above, in "Capacity content — design decisions") being correctly configured. Fixed by giving `statusAt(transitions, atMs, currentStatus)` a third parameter — the issue's actual current status (now captured as `currentStatus: issue.fields?.status?.name` in both `extractRawSprintData` and `extractIterationIssueData`) — used as the zero-transitions fallback instead of the literal string `'unknown'`: since the issue has never changed status, its current status **is** its status at any point in its history, including `atMs`. Fixed at both call sites (`computeBurndown`'s phase lookup and `computeIterationCommitted`'s whitelist check), since `statusAt` is explicitly a shared primitive — not just the one that was reported. **Known, deliberately not fixed in the same pass:** `computeVelocity`/`computeIterationVelocity` have the same class of bug for a *Done*-mapped zero-transition ticket (`issue.transitions.find(t => ... === 'done')` finds nothing, so it's never counted as velocity) — narrower in practice (requires a ticket to be created already-Done, e.g. via bulk import, rather than just created into whatever status a team happens to start work in) and not what was reported, so left alone rather than expanding this fix's scope.

10. **`getIterationActiveRawData`'s "long-running issue" query had no time bound at all for Done tickets, and timed out on real Kanban projects.** Its `status IN (...)` discovery query was built from `isTrackedPhase(phase)`, which only excludes `backlog`/`excluded` — it does *not* exclude `done`. So the query was actually `status IN (<every dev/blocked/review/test/done status>)`, unbounded by any date, with `expand: changelog` on every match: on any project with real history, that's every issue ever closed, full changelog and all. Confirmed by a giveaway already in the code: `isActiveDuringWindow`'s transition-loop check reads `if (isTrackedPhase(phase) || phase === 'done') return true;` — the `|| phase === 'done'` is dead code against the actual `isTrackedPhase` definition, meaning `isTrackedPhase` had clearly drifted from an original WIP-only meaning. The same drift was a second, independent correctness bug: `isActiveDuringWindow`'s "phase at window start" check also used `isTrackedPhase`, so an issue already Done *before the iteration even started* counted as "active during the window" if it merely got touched (a comment, a label) sometime inside it — invisible in Burnup (delta-from-day-0 cancels a static value) and Rework (only counts in-window transitions), but produced spurious extra rows in Cycle Time, built from that issue's entire unrelated history. Fixed 2026-08-11 by splitting the fetch into three JQL queries instead of two: (A) touched-during-window, now also excluding backlog-mapped statuses; (B) currently mid-flight — a new `isWipPhase(phase)` predicate (`dev`/`blocked`/`review`/`test` only, no `done`) — bounded by `created <= paddedEnd` so a brand-new ticket can't leak into an old iteration's report; (C) reached a done-phase status *during the window specifically*, via `status CHANGED TO (...) DURING (...)` — the same bounded-changelog-scan pattern `getIterationCommittedRawData` already used for exactly this kind of query (see the comment above it), which is what lets an issue that genuinely finished mid-iteration back in without reintroducing the unbounded scan. `isActiveDuringWindow`'s window-start check was switched from `isTrackedPhase` to the same new `isWipPhase`, fixing the Cycle Time correctness bug as a separate, deliberate change from the query fix (so the two effects — fewer issues fetched vs. differently classified — stay distinguishable if something looks off later). The three queries now also run in parallel (`Promise.all`, previously a sequential loop), and `fetchIterationIssues`'s page size went from 50 to 100 (shared helper, so this also speeds up `getIterationCommittedRawData`/`getIterationVelocitySp`). **Known, accepted tradeoff from the backlog-status exclusion in query A:** an issue genuinely worked during the window that gets reverted to a backlog status before the fetch runs is no longer picked up by any of the three queries — requested explicitly by the user, not an oversight.

11. **`computeScopeFoundation` double-counted every carried-over sprint ticket's SP as a same-day scope-change "add" event.** Committed scope (`initialCommitted`) already counts any ticket whose Sprint-field "added" event lands at or before `sprint.startDate + graceWindowHours` (default 12h) — this is precisely how a carry-over shows up: closing a sprint and carrying its unfinished items into the next one logs a Sprint-field change timestamped right at (or within seconds/minutes of) the new sprint's start. But the very next loop, building `scopeDeltaByDay`, applied **every** sprint add/remove event as a same-day delta unconditionally, with no check for whether that event was already folded into the committed baseline above it. So a carried-over ticket got counted twice: once correctly as committed scope, once again as a spurious "scope added" bar/event on day 1 — reported 2026-08-13 as TRI Scope Change showing carry-over tickets as day-1 scope change, confirmed against real data (team ZEN, Sprint 11: ZEN-1123/1127/1129 all logged their Sprint-field carry-over at `2026-08-12T20:41:39+10:00`, ~2 minutes after Sprint 11's actual `startDate`, comfortably inside the 12h grace window). Not a timezone bug — a genuine grace-window logic gap, same *class* of double-count as bug #1 above but for the add-inside-the-window case rather than the add-before-the-sprint-existed case. Fixed by skipping any sprint add/remove event at or before `cutoffMs` in the `scopeDeltaByDay` loop (`src/index.js`, inside `computeScopeFoundation`) — those events are already reflected in `initialScope`, so re-applying them as "change" contradicts the grace window's whole purpose. Since `computeScopeFoundation` is shared, this one-line fix corrects **both** TRI Scope Change (chart bar + events-table row) and TRI Burndown (`runningScope` was inflated by the same double-count starting day 1) — `computeScopeChangeData`'s separate events-table loop needed the identical skip added directly (it rebuilds event rows independently of `scopeDeltaByDay`, using the same `graceCutoffMs` computeScopeFoundation already returns). **Deliberately left alone in the same pass:** the "excluded" (Not Required) transition a few lines below has an analogous unconditional-timing gap, but it's a different mechanism (a status transition, not sprint membership) and wasn't what was reported — confirmed with the user to scope this fix to add/remove events only. Velocity is unaffected (already reads `currentStatus` only, no `computeScopeFoundation` dependency, per the 2026-08-12 rework above).

## Known, accepted limitation (not yet fixed)

`getSprintRawData`'s issue+changelog pagination has no cap on issue count or page count. Tested and working with a ~100-issue sprint. Documented in `README.md`'s "Known simplifications" as a real scaling risk (possible Forge function timeout on much larger sprints), not silently ignored — but not fixed either. If this becomes a real problem, the fix is either a hard cap with a clear "sprint too large" message, or moving to incremental/background fetching.
